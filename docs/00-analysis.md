# Pre-Coding Analysis：Kmai 前端

## Step 1：影響範圍搜尋

目前 repo 尚無應用程式程式碼，只有下列需求與設計基準：

- `funtion-list.md`：原始功能清單，共涵蓋員工端、內容管理、AI 設定與系統管理。
- `PRODUCT.md`：產品定位、使用者、成功條件、設計原則與 WCAG 2.2 AA 承諾。
- `DESIGN.md`：seed 視覺方向，Creative North Star 為「The Living Field Guide」。

因此本次不是修改既有元件，而是初始化 Vue 3 SPA 並建立完整前端骨架。

## Step 2：邊界條件與風險

1. **初次使用與角色差異**：一般員工不可看到技術設定；管理者入口需明確，但不能讓首頁被管理功能干擾。採角色式路由與不同導覽群組。
2. **搜尋無結果與 AI 不確定性**：搜尋需區分初始、載入、無結果與錯誤；AI 回答必須顯示引用、處理狀態與「可能不完整」提示，不假裝絕對正確。
3. **大量管理功能造成認知負荷**：不將每個功能做成獨立頁面。依工作流程合併為文件、處理、圖譜、回饋、AI 設定、存取控制與系統管理工作區。
4. **Mock 狀態與未來 API 落差**：Mock 資料使用明確型別與 repository/service 邊界；畫面不直接 import JSON，日後可替換為 API。
5. **響應式與資料密度**：員工核心流程需支援 375px；管理表格在窄螢幕改為摘要列或可水平捲動區，且不能遮住鍵盤焦點。
6. **破壞性操作**：刪除、拒絕、取消處理與重建圖譜需確認；成功後提供可見結果，不只用短暫 Toast。
7. **表單可用性**：欄位有永久 label，失焦或送出後顯示可修正的錯誤；送出期間停用以避免重複提交。
8. **依賴安裝**：Vue、Vite、Vuetify、Vue Router、Pinia、Material Design Icons、Vitest 與相關工具需從套件來源安裝，可能需要網路權限。

## Step 3：適用規範與架構

- `ui-ux-pro-max`：採瑞士式極簡、單一靛藍重點色、標準資訊密度、低動態；搜尋具自動建議與可行動的無結果狀態。
- `impeccable`：以 PRODUCT.md 與 DESIGN.md 為視覺決策來源，拒絕通用 AI SaaS 樣板與卡片牆。
- `frontend_architect` CASE B／C／G：Vue 3 `<script setup lang="ts">`、強型別、語意化元件、鍵盤與 ARIA 支援。
- `ux_heuristics` CASE A／B／C／D：表單、Loading/Error/Empty、導航與新頁面皆依 Nielsen 原則檢核。
- 樣式方案：只採 Vuetify 3 與集中式設計 tokens；不混用 Tailwind，純 CSS 限於版面結構、閱讀寬度與品牌細節。

### 技術架構

- Vue 3 + Vite + TypeScript
- Vue Router：路由、角色 metadata、頁面標題
- Pinia：登入狀態、介面偏好、AI 對話與管理選取狀態
- Vuetify 3：主題、表單、資料表、Dialog、Navigation、Skeleton 與響應式基礎
- Mock repositories：以 Promise 模擬載入與錯誤，保留未來 API 替換點
- Vitest：核心搜尋、文件 ACL、AI 對話與路由存取規則測試

## Step 4：修改原因與決策

**核心問題**：原始清單功能完整，但若逐條轉成導覽項目，員工會不知道從哪裡開始，管理者也會在大量技術名詞中迷失。

**採用方案**：以「找答案、讀文件、維護內容、處理異常、設定系統」五類工作意圖重組資訊架構。員工首頁保持 Google 式直接；AI 是搜尋後的自然延伸，不是整個產品唯一入口。管理端使用任務型工作區與分頁，將設定依責任集中。

**選擇 Vuetify 的原因**：本產品需要大量表單、資料表、Dialog、選單、Skeleton、深色模式與無障礙基礎，Vuetify 能以較少自訂 CSS 維持一致性。Tailwind 與 Vuetify 同時使用會形成兩套 tokens 與間距語言，因此不納入。
